# AOMS 2.0 — Iteration 19: персональные административные учётные записи

## Реализовано
- Таблица JSON-строк `admin_users` поверх существующего SQLite-адаптера; отдельная схема БД не создаётся.
- Логины нормализуются; пароль не хранится в открытом виде — используется salted scrypt (64-byte derived key).
- Подписанная HMAC-SHA-256 сессия `v2`, срок действия 12 часов; прежний shared-password cookie временно принимается для обратной совместимости.
- При первом входе с `ADMIN_PASSWORD` (не короче 12 символов) автоматически создаётся `ADMIN_USERNAME` или `admin` с ролью `super_admin`, если таблица пользователей пуста.
- Страница `/users` и API управления пользователями: создание, изменение имени/роли, включение/отключение, сброс пароля.
- Нельзя отключить или понизить последнего активного Super Admin.
- Для новых сессий маршрутный доступ ограничен ролью; API пользователей и журнал аудита проверяют разрешения.
- Новые действия управления учётными записями пишутся в Audit Log; пароли и их хеши в журнал не попадают.

## Порядок миграции
1. Сохранить текущие `ADMIN_PASSWORD` и SQLite Volume без изменений.
2. Не менять и не удалять `ADMIN_PASSWORD` до первого успешного входа после обновления.
3. При первом входе указать `ADMIN_USERNAME` (если не задан — `admin`) и текущий `ADMIN_PASSWORD`; приложение создаст bootstrap Super Admin.
4. После входа создать дополнительные персональные учётные записи на странице «Пользователи и роли».
5. Проверить вход новой учётной записью в отдельной сессии. Старый общий пароль пока остаётся механизмом совместимости; его отключение требует отдельной проверенной миграции.

## Ограничения и незавершённые проверки
- Сессии пользователей не отзываются мгновенно при отключении аккаунта или смене роли: подписанный токен действует до 12 часов. Смена `ADMIN_SESSION_SECRET` (или `ADMIN_PASSWORD`, если отдельный секрет не задан) инвалидирует все сессии.
- Старый legacy cookie продолжает иметь права Super Admin до истечения своего срока или logout. Удалять `ADMIN_PASSWORD` сразу после релиза нельзя.
- Старые server actions и API должны пройти полный аудит разрешений; текущая проверка маршрутов не заменяет проверку каждого бизнес-действия.
- TypeScript и production build не запускались: зависимости Next.js отсутствуют в рабочей среде. Нужна staging-проверка миграции и входа на копии SQLite до production.
