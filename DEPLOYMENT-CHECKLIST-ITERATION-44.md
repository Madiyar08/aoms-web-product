# AOMS 2.0 — безопасный чек-лист перед деплоем

Этот чек-лист не выполняет деплой автоматически. Production Railway, volume и SQLite должны оставаться нетронутыми до прохождения проверок ответственным сотрудником банка.

## 1. Подготовка

- [ ] Зафиксировать текущий production commit и переменные окружения (секреты не копировать в Git/отчёты).
- [ ] Проверить, что Railway Volume смонтирован по согласованному пути.
- [ ] Убедиться, что `AOMS_SQLITE_DB_PATH` указывает на файл внутри постоянного volume.
- [ ] Создать резервную копию production SQLite по внутреннему регламенту банка.
- [ ] Скопировать backup в изолированную staging-среду; не использовать production-файл для тестов.

## 2. Проверка кандидата на релиз

- [ ] Node.js версии 22.5 или выше.
- [ ] `npm ci --include=dev` завершается успешно.
- [ ] Все тесты проходят.
- [ ] `npx tsc --noEmit` завершается успешно.
- [ ] `npm run build` завершается успешно.
- [ ] Проверены все переменные окружения и секреты; реальные значения не хранятся в репозитории.
- [ ] На staging выполнен вход под каждой ролью и проверены запреты на прямые API/Server Action вызовы.
- [ ] На копии базы проверена миграция, запуск, повторный запуск и откат по утверждённому плану.

## 3. Интеграции и восстановление

- [ ] Telegram webhook использует HTTPS и `TELEGRAM_WEBHOOK_SECRET` длиной не менее 32 символов.
- [ ] Проверена отправка тестового сообщения и медиа в тестовый канал.
- [ ] Проверена повторная доставка после временной ошибки Telegram.
- [ ] Проверено восстановление очереди после перезапуска staging.
- [ ] Проверен Yandex Routing API только при наличии действующего ключа; без ключа подтверждён безопасный fallback.
- [ ] Проверены Android/iOS Telegram Mini App, разрешения камеры/GPS и повторная отправка после потери сети.

## 4. Контролируемый релиз

- [ ] Получено одобрение владельца системы и ответственного за БД.
- [ ] Назначено окно релиза и ответственный за откат.
- [ ] Deploy выполняется через обычный GitHub → Railway pipeline.
- [ ] После деплоя проверены healthcheck, вход, мониторинг, создание тестового задания и чтение данных.
- [ ] Проверено, что данные сохраняются после перезапуска контейнера.
- [ ] При любой потере данных, ошибке миграции или критической ошибке доступа — остановить релиз и выполнить утверждённый rollback.

## 5. Важные запреты

- Не удалять и не пересоздавать Railway Volume.
- Не менять `AOMS_SQLITE_DB_PATH` без отдельного плана миграции.
- Не запускать тесты, очистку или миграции против production SQLite.
- Не помещать `.env`, токены Telegram, API-ключи и дампы реальных данных в GitHub или ZIP для передачи.
